How to test a server-sent events (SSE) endpoint in the browser

In RequestFox, a browser extension for Chrome, Edge and Firefox, open Compose, type the endpoint's address and press Send. A server-sent events response stays open: the status line says Streaming… with a count of events, each event is listed as it arrives, and Stop ends the read and keeps what came. On a recorded call, RequestFox flags a stream that sent an error event, one that closed without its end marker, and one that went quiet for a long time. Headers and auth go in like any other request.

For RequestFox 2.5.0, checked 19 November 2026. The event stream format is from the HTML standard, checked 20 November 2026; source below.

How do I test a server-sent events endpoint?

  1. Open Compose and type the address

    Press Compose in the top bar, choose the method (usually GET) and type the endpoint's address. Add the headers the server wants, such as an Authorization header, in the Headers tab, or set the auth in the Auth tab.

  2. Press Send

    Press Send. When the response is an event stream, the status line says Streaming… with the number of events so far, and the events fill in below it.

  3. Stop when you have seen enough

    Press Stop on the status line. RequestFox ends the read and keeps the events up to that point; the line says the status and how many events were kept.

  4. Read the events

    Each event shows its fields. For a language model's token stream, the label Token stream shows, with the text the tokens add up to under Text. A long stream keeps its newest events within the body limit, and a note says how many are shown.

What does RequestFox flag in a stream?

  • Stream error: the stream sent an error event inside its 200 OK (an event: error, or an event whose JSON is an error). The card shows the error's own message.
  • Ended early: a stream with a known end marker, such as the [DONE] of a language model's stream, closed without it, so the response may be cut off. It is checked only for streams RequestFox recognises as that kind.
  • A paused badge, with the longest gap: the stream stopped sending for a long time between two events. The note says the longest pause and how many pauses of 5 seconds or more there were.

These flags are on the call's card in the log, for streams a page reads while you record. An event stream is text with the type text/event-stream; events are separated by a blank line, and the fields are event, data, id and retry [1]. A browser drops a last event that has no blank line after it [1], and RequestFox says so on that row.

Can I see the events my own page receives?

Yes. Press Start Recording and use the page. A stream it reads with fetch, XMLHttpRequest or EventSource stays open as a row that fills as events arrive, and is kept when you stop. Connections the page opened before you pressed Start are not seen: reload the page. WebSocket / SSE activity in the top bar lists the page's socket and event-stream messages. For an EventSource, the rows are the event types the page listens for: the browser hands a page no others.

What if no events show?

  • The response is not an event stream. A server has to answer with the type text/event-stream [1]; check the response headers on the card.
  • The server sends events only when something happens. The status line keeps saying Streaming… until the server sends one, or you press Stop.
  • It stopped on its own. The card says why: the stream broke off with a network error, the page closed it, or recording stopped while it was open.
  • A last event is missing. If the server did not end it with a blank line, a browser drops it [1].

Sources
