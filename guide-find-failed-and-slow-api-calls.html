How to find failed and slow API calls in Chrome

Open DevTools (Ctrl Shift J), click Network, choose Fetch/XHR, tick Preserve log, then sort by Status to see the failed calls and by Time to see the slow ones. You don't need to install anything. But a call that fails inside a 200 OK still looks fine there. RequestFox, a browser extension, counts the failed and slow calls while you use the site, and marks the ones that fail inside a 200.

For RequestFox 2.5.0, checked 19 November 2026. Facts about Chrome are from its own documentation, checked 4 November 2026; sources below.

How do I find failed and slow requests in Chrome DevTools?

  1. Open the Network panel

    Press Ctrl Shift J (Cmd Option J on a Mac), then click the Network tab [2]. DevTools only records requests while it's open [2], so open it before you do the thing that breaks.

  2. Show only API calls

    Click the Fetch/XHR button among the type filters [1]. Tick Preserve log, and DevTools keeps the requests across page loads until you untick it [1]. Without it, a page that reloads after the error clears the list.

  3. Find the failed calls

    Click the Status column header to sort by it [1]. The column shows the HTTP code, for example 200 or 404. A request that failed before it got a response shows (failed) followed by the error message, and a CORS failure shows CORS error [1]. To see only one code, type status-code:500 in the Filter box [1]. To see everything except what the filter matches, tick Invert next to the box [1].

  4. Find the slow calls

    Click the Time column header to sort by it [1]. Time is the total duration, from the start of the request to the last byte of the response [1]. To sort the Waterfall by a different timing, right-click the table header, hover Waterfall and pick Start Time, Response Time, End Time, Total Duration or Latency [1]. To find big responses, filter with larger-than:1000; larger-than:1k works too [1].

  5. See where the time went

    Click a slow request and open its Timing tab [1]. The phases include Queueing, Stalled, DNS Lookup, Initial connection, Request sent, Waiting (TTFB) and Content Download. Waiting (TTFB) is the time the browser waits for the first byte of the response. It includes one round trip of latency and the time the server took to prepare the response [1].

  6. Search every response

    Press Ctrl F (Cmd F on a Mac) in the Network panel. The Search tab opens and looks through request headers, payloads and responses. Click a result and the matching request is highlighted [1]. It's a quick way to find which call returned an error message you saw on screen.

What can DevTools not show me?

  • One call at a time. You sort and read a long table, then open each suspect to read its response. The table doesn't count how many calls failed or were slow.
  • Errors inside a 200. The Status column shows the HTTP code. An API that sends a 200 and puts the failure in the body, as GraphQL does, looks fine in the list. You find it by opening the response, or by searching for the error text. GraphQL errors in a 200 OK.
  • It only keeps what you watched. DevTools records while it's open, and you have to tick Preserve log before the page moves on.
  • The cause is a separate hunt. For a request started by a script, the Initiator column links to the line in the source file [1], and you follow it by hand for each call.

How does RequestFox find them for me?

  1. Press Start Recording, then use the site. Every API call shows up in the panel, with the failed, slow and repeated ones marked. How to record API calls.
  2. Read the counts. Above the calls are buttons for Duplicate, Failed, Slow and JS errors. Click one to see only those calls, and click it again to see them all.
  3. Know what counts as Failed. A call is Failed when its status is 400 or higher, when it never got a status (connection refused, a CORS block, aborted), or when the response says it failed inside a 200 OK: a GraphQL errors list, a JSON-RPC error, a SOAP fault, an error event inside an event stream, or a gRPC status other than OK. Those calls carry their own mark, such as GraphQL error, so you can tell them from a plain 500.
  4. Know what counts as Slow. A call is Slow when it takes longer than your slow limit. The limit starts at 3 seconds, and you change it in Settings under When to flag a call, in the box Flag a call as slow after (ms). The Slow mark on a card says the limit in its tooltip.
  5. Check Repeated problems. When endpoints keep failing or being slow, they are listed above the log under Repeated problems, with how many times each failed or was slow, so one bad endpoint doesn't get lost among hundreds of cards.
  6. Open a call to see why. Its Timing section shows where the time went: queued, DNS lookup, connect, waiting for the server, download. For a call to another site, the browser hides the breakdown unless that server allows it, and the card says so. Called from lists the page code that made the call.
  7. Send it again. Press Replay on a card to resend that exact request and see whether it still fails. For a POST, PUT, PATCH or DELETE it asks first, because a repeat can change real data. Replay and edit a request.

RequestFox marks what it sees, and you decide what's a bug. A call that your own mock or fault rule changed is marked Mocked or Simulated, so a test you set up isn't mistaken for a real failure.

Which should I use when?

You want toUse
Look at one call right now, with nothing installedDevTools. It's built in, exact, and shows every phase of a request.
Filter by one status code or one sizeDevTools. The Filter box does that in one line.
Know how many calls failed or were slow in a whole sessionRequestFox. The counts sit above the log, and you can click them.
Catch a failure the status code hidesRequestFox marks GraphQL, JSON-RPC, SOAP and stream errors in a 200. In DevTools you read the body.
Find the code that made a call, or send it againRequestFox: Called from and Replay on the card.
Keep the evidence after you close the tabRequestFox keeps each session in History. Send a bug report with the evidence.

They work together: DevTools for the exact one-call view, RequestFox for the whole session. RequestFox vs DevTools Network.
