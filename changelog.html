Changelog

What changed in the newest RequestFox releases, newest first. This page is built from the project's own changelog, so it says exactly what shipped. The current version is 2.5.0.

Releases

Newest first. The browser updates the extension by itself.

2.5.0 19 November 2026

In short. Mock is a button on every call: press it, change the response, press Mock it. Settings opens on Mocks & rules and every screen shows less at first. Secrets are hidden in more places, and an export that still holds one asks first.

New for you in this release

  • After you install, one welcome page says where the panel is (the toolbar icon; in Chrome, pin it from the puzzle menu) and the three steps to start. It opens once, never on an update.
  • The first screen asks for nothing but Start Recording: the session name and the reload option wait under Options.
  • A recording covers the tab you start it on, wherever it goes (a sign-in on another site included), and the other tabs of that window while they show the same site. To record every tab of the window, tick Record every tab in this window, whatever site it shows in Settings, What gets recorded.
  • After Stop a mock says Mock paused and answers again at the next recording; Delete mock removes it, and one All rules switch pauses every rule at once.
  • Help keeps its tours short; behind All tours it now has What's new in 2.5 and Report a problem…, which opens your own mail program with three questions, or copies a short diagnostics text, and sends nothing itself.
  • Open in a tab (Help, More help) opens the whole panel in a browser tab. There, in a wide window, Compose shows the response beside the request, and the log starts as the table.
  • The command-line tool reads an environment variable only when you allow it (--allow-env NAME); without it, a config that reads one stops with one sentence that names the flag (exit 2). It also carries the MCP server (node requestfox-ci.mjs mcp), so a store install has it: Settings, MCP control, Download the CLI.

Mocking

  • Mock is a button on every request card, next to Replay, not an item at the bottom of its ··· menu. It opens a dialog that holds the response the server sent: change the Status (200 to 599) or the Body, then press Mock it. A call that got no response (the backend is down) starts as 200 with {}. Reload the page or repeat the action to see the mocked response.
  • The card then says Mocked. Its menu edits the response, keeps the mock on without recording, turns it off or deletes it; a mock that is off says Mock off, with Turn on. More options… in the dialog opens the full rule in Settings with what you typed, and Keep it on without recording… saves it into a mock set for that site.
  • A mock made from a call answers that address and only that one: past cache-busters (_=, and t= or ts= only with a made-up value), a hidden query value (a redacted ?key= stands for any value), a redirected call (the address the page asked for), a page with <base href>, a call the page makes while it loads, and a reload after the browser let the extension sleep. It wins over an older, broader rule. A GraphQL mock answers only its operation, persisted queries included.
  • Match has Pattern with \* (/api/users/* answers every user), and a mock can wait before it answers (Delay ms). The rule editor shows a mock's GraphQL operation, its Content type and the recorded headers it sends back; a status outside 200 to 599 is refused, and a body that is not JSON is flagged.
  • Replay and Compose always call the real server, and the card says so ("Not mocked"). A call a mock should have answered says why it was not: the mock is off (with Turn on), the page called before RequestFox was ready, or the page did not make the call itself. Page files and EventSource streams, which a mock cannot answer, have no Mock or Block.
  • A mocked response reads like a real one: a synchronous XMLHttpRequest gets it at once, with the status text, responseURL, the page's responseType and progress events; a HEAD response has no body.
  • Mocks on (n) counts only the rules that can reach this recording. Mock and break rules go only to the tabs you record, and Stop clears them.
  • Mock sets keep their exact addresses through export and import. The workspace export asks before it writes secrets held in mock rules. MCP create_rule and update_rule take match: "exact", and editing a mock made from a card keeps its address and GraphQL operation.
  • A new rule mode, Change the response: the real call goes out and the page gets the response with one text or JSON field replaced ($.price). No script, so it works in Firefox too, and in mock sets.
  • A script rule can Respond without calling the server: the script writes the whole response and the real server is never asked.
  • Mock the calls shown in the log… (under the mock sets) makes one exact mock for each call the log shows, with its newest response, in one new mock set that is off until you turn it on. A rule's row says how many calls of this recording it answered.
  • A mock can answer Only when the request body contains a text or a JSON field ($.method = getUser), so one JSON-RPC address can have a mock per action. Load the body from a file… fills the Body, and a mock made from an image or other bytes answers with those bytes.
  • A mock's Response headers are rows you can edit, add and remove; a header no page can read (Set-Cookie) or a name a browser cannot send is refused by name. The response breakpoint now pauses XMLHttpRequest responses too, and its Headers box changes the response's headers.
  • Find a rule appears once you have ten rules. Compare anyway makes a rule compare a query value it would otherwise ignore because it changes on every call (?from= with a time).
  • Esc in a breakpoint now lets the paused call go on unchanged (it used to abort it); only Abort stops it, and once you have changed something Esc asks you to press Resume or Abort.
  • Closing Settings with a rule or a set half typed asks Save what you typed? first. Save and keep on saves a mock set and switches it on in one step.

Easier screens

  • Settings opens on Mocks & rules, and its rows come in the order people need them: Mocks & rules, Appearance, Notifications, What gets recorded (was Noise filters), Privacy & evidence, When to flag a call (was Detection thresholds), Full, Background or Mini (was Panel mode), and a new last row, Sign-in, cookies & connections (OAuth 2.0 and the vault, the cookie jar, the issue tracker, MCP control).
  • Mock sets and header-rule sets sit inside the group whose rules they keep on, under Keep some mocks on without recording and Keep some rules on without recording, and are called sets; saved threshold sets sit in When to flag a call. An OAuth 2.0 profile is now a sign-in, everywhere you read it.
  • A Settings group opens on one short line per hint, with the rest under More about this. The vault passphrase waits behind Vault passphrase… until it is needed. Each switch says On or Keep on beside it. Nothing shows under the Done bar, and Settings never scrolls sideways.
  • The live log starts higher: "9 calls" on one line, two or more repeated problems fold into Repeated problems: N, and each one says it once, in words ("GET /api/data · failed 3×"). The table's sort hint shows only until the first sort.
  • A failed call's card opens on why it failed: its Response, else its Details. Overview rows carry their finding codes in the tooltip only.
  • After Stop, one quiet line says the session is over and what it kept. Over an open panel, the start bar is one slim row with a quiet Start.
  • The card menu says Copy as cURL, and Edit and send again… comes before Open in Compose. The search box says "Search calls, e.g. 500 or /login", and its help button is Search tips.
  • The first-run tour is three plain slides that name Replay and Mock. Help opens on a short list, How to mock a call among them; the rest wait behind All tours.
  • At 480 px and wider, Compose, History and Timeline carry a short word in the top bar.
  • Compose: the response says its status once, with Hex and Save as example under ···; the five tabs fit one row (measured in ten languages). Long hints are one short line, and an auth field never repeats its label as a placeholder. Performance opens on Summary, then Slowest endpoints, and its five tiles read 3 + 2 at 360 px. An empty suite shows only how to add a step.

Privacy

  • A recording of a private (incognito) window is kept in memory only: it is never written to disk or to History, and one line in the recording bar says so ("Private window: this recording is not saved. Export it before you close the window.").
  • One set of redaction rules for every path: the log, History, HAR, the report, CSV, Postman, Copy as cURL, a bug report and the files you share. It now also hides form and multipart fields (user[password]=), numbers under card, CVV, OTP or PIN names, XML and SOAP values, HTML hidden inputs, GraphQL arguments, Bearer tokens and JWTs anywhere in a text, user:pass@ in an address, and the secrets in Location, Link and Referer addresses. Thirteen credential headers are hidden by name.
  • History → Open file hides the tokens, passwords and cookies in a HAR or session file, as your Redact setting says. Playwright, Cypress and issue titles carry no query values.
  • Exporting a session that still holds secrets asks first: Export with secrets hidden (the default) or Export as it is. The export offered at Stop always hides them.
  • An OAuth client secret is kept encrypted in the vault, not in plain storage.
  • Cookies imported from the browser into the cookie jar stay in memory until the browser closes, unless you tick Keep imported cookies after the browser closes for that site.
  • A click's label never holds what was typed in a field. An alert about a call is shown in full only in that call's tab. No raw ?access_token= address is written to disk while redaction is on, and the background logs no call addresses.
  • The page script reads the extension's messages through a getter it keeps from the start, so a page cannot read them by patching the browser.
  • The privacy policy says what the recording scripts do while recording (they load in every tab and report only from the tabs you record), that webRequest reads the request body, and that the opt-in screenshot uses the site access. Its contact address is in section 8.

Client

  • A suite step whose status check expects an error (status = 404, say) passes when the server sends that status; before, any 4xx or 5xx failed the step. The panel and the CLI judge it the same way.
  • A Postman, Insomnia, Bruno or Hoppscotch file with folders imports as a folder of collections, one per folder. Import as one flat list instead, in the dialog that ends the import, brings it in as one collection.
  • A folder's ··· menu has Run as a suite… and Export…: the whole imported file runs as one suite, or goes back out to Postman, Bruno, Insomnia or Hoppscotch as one file with its folders.
  • A curl command pasted into Compose's address fills the method, address, headers and body.
  • A new vault passphrase is typed twice, and Forgot the passphrase? says what can be done.
  • A suite run's result rows open to every check with what it got, and have Open the response and Copy results.
  • Under Compose's address a line says where the request goes (Sends to …) or which variable the environment lacks (Not set in “Staging”: id).
  • Bruno and Thunder Client assertions come in as checks.
  • A suite's data table can be pasted from Excel (tabs, or ;) or be a JSON file, and a data-driven run works with no environment too.
  • Two changes in how a request is sent: a JSON body with no Content-Type header goes out as application/json (Compose says "Sent as …" under the body; add a Content-Type header to change it); and a request's Auth can be From the collection, while No auth now means no auth is sent, even when the collection has one.
  • Follow redirects (on by default): off, a request stops at a redirect and shows its status and Location. Time limit (s) in Advanced stops a request that takes too long, and says so; empty means no limit.
  • A File body sends one file as the whole body (up to 15 MB).
  • Cookie, Origin, Referer, User-Agent and Accept-Encoding headers you type are sent as typed, on RequestFox's own requests.
  • Importing a collection says what was Not kept, and an import over an existing collection can replace it (the old one goes to Recently deleted); Insomnia environment variables come along.
  • OAuth 2.0 is in Compose's Auth list: pick a saved sign-in and Compose sends its token; with none saved, Set up a sign-in… opens the form. Collection and folder settings offer it too.
  • Send on a saved row opens that request, then sends it. Closing a changed request offers Save and close, and so does opening a sixth request while the oldest has changes.
  • A 4xx or 5xx response is never shown in success green, also for a send an MCP client started. A response with no body says "No body.", and the link after a send reads Save request….
  • A trip from Compose into Settings comes back to Compose. "Recently deleted" closes again, a URL the panel fills in reads from its start, and the linked line's Unlink says "Stop using its settings".
  • A Form (URL-encoded) body fills each {{variable}}, then encodes it: a password or client secret with +, & or % goes out as typed, in Compose, a saved request's Send and a suite step.
  • An address with no http:// (localhost:3000/api) gets it, and the address box shows what is sent; a path alone with nothing recording says to write the whole address.
  • A request kept over a reload says when it still holds *REDACTED*, and Send stops there (with Send anyway). Its saved header and token come back from the saved request, so Save changes keeps them.
  • A {{name}} that came with a recorded call (the log, a past session, a HAR) or a link in a response is the page's text: Send leaves it as text, so a page can no longer have your variables or vault secrets filled in and sent to it. The status line names them, with Fill with my values.

Protocols

  • WebSocket: up to 5 connections at once, headers for the opening handshake (with the server's response under Show headers), Socket.IO v2 as well as v3 and v4, binary messages sent from hex or saved as a file, Copy on one message, Copy log, Socket.IO binary arguments ({"$binary": "…"}), and saved WebSocket requests.
  • gRPC: error details decoded, live stream rows, "Fields of" a message (nested ones too), Show default values, the loaded .proto files under Files (n) with one × each, and grpcurl and buf commands under Copy as code.
  • SOAP: a SOAP Fault shown as one, rpc/encoded services, and WS-Security (UsernameToken) in the Auth list.
  • MCP server tester: Sign in… when a server asks for it, a server's question (elicitation) answered with a form under The server asks, with Decline, the older HTTP+SSE transport, resource templates, and a check of a tool's result against its output schema.
  • GraphQL: subscriptions over SSE as well as WebSocket (over WebSocket, their headers go with the handshake too), and three more checks on a query before it is sent.
  • Examples: New example and Edit on a saved request's examples, and Mock with this… on each one: the Mock dialog with that example filled in, then Mock it (a browser mock in two clicks). A workspace import that would drop some of your requests asks: Import keeps them, Replace with the file's does not, and Undo import puts everything back. Suites travel in the workspace file.

Exports and CLI

  • The CLI no longer prints tokens, cookies and passwords into CI logs or the JUnit file: a check on a secret-looking value prints hidden (51 characters), equal (hidden) or differs (hidden), and still passes or fails as before.
  • -h is help wherever it stands, as --help is. The README lists all twelve commands and the exit codes: a request that could not be sent is 1, a command that could not run is 2.
  • The CI export, the workspace folder and mock sets hide every secret name the log hides (CVV, IBAN, TOTP, passphrase and more).
  • "Same response as last time" keeps the ids that pick the resource in a request's key (a GraphQL query for user A and for user B were one request). Such requests save a new first response once.
  • requestfox-mcp --http needs a token by default. Without --token or REQUESTFOX_MCP_TOKEN it makes one at each start and prints the header your MCP client must send, Authorization: Bearer <token>, once on stderr. --no-token turns the check off for local scripts.
  • The MCP server ships inside the one-file CLI, so a store install has it too: node requestfox-ci.mjs mcp (stdio) or mcp --http 3333 --control for MCP control. Settings, MCP control says how to connect in three steps and has Download the CLI.

Fixes

  • Firefox: Settings no longer shows a "Slow down the whole tab" row (Firefox cannot do it), and the rule editor says so where it matters; a CORS-blocked call shows only its CORS pill.
  • "Replay from the extension" shows once on a CORS card, not twice.
  • An XMLHttpRequest the page opens before its rules are known can still be held by a rewrite script, and the console says the real reason when it can't.
  • Plain words for "36 of 37", "Columns (1 from response)" and the Timeline's "Typical 27 ms · Slowest 5%: 4.0 s".
  • Settings keeps no stale result lines, does not glide under reduced motion, and shows no group header over a single rule group.
  • "Open the vault" and a sign-in refused for a locked vault open Vault passphrase… first, so the field is there to type in.

Open requests

  • Compose keeps up to five requests open at once, as plain chips above the URL. Opening a captured request (from the log or a past session), a Recent send, or New request (in ··· More, or the + after the chips) while another request is open puts it in a chip of its own instead of over the one you were writing; something already open shows its chip, with your edits. The strip only appears once a second request is open.
  • Each request keeps its own form, status line and answer. A send still out in a request you left finishes there; its answer is under it when you come back, not under the one on screen.
  • A dot after a chip's name says it has changes that are not saved; closing it asks first. × or a middle-click closes a chip. On a chip, Delete closes it and Esc closes the one on screen (Esc in a field still closes the panel). Ctrl/Cmd+W and Ctrl/Cmd+Tab stay the browser's: it reserves them, so the panel never takes them.
  • A saved request opens in Compose with a click on its name in its collection, tied to the collection (Send uses its settings). One already open, from there or from Recent, is shown instead of opened twice.
  • At 300 px the chips scroll sideways with no scrollbar (a mouse wheel over them moves them along), and an edge with more chips past it fades. A long name is cut with … inside its chip, and its tooltip has the whole request.
  • The strip is a tablist for the keyboard and screen readers: Tab reaches the chip on screen, the arrow keys (right to left in Arabic) and Home/End move along it and show the request reached, Delete closes the chip. A chip says its name and whether its changes are saved; closing one from the keyboard says which request is now on screen.
  • "Save to collection…" makes the request that saved request: named like it and tied to it. A saved request with changes gets Save changes in ··· More, which writes them into it (its name, notes, examples and checks stay).
  • Open requests come back when the panel opens again, the one on screen too, with their changes. A typed secret (a token, a password, an API key: the same rule as Recent) is never written to disk; a request opened again says which ones to type in again. A saved request with no changes comes back as it is saved in its collection now. A text over 100,000 characters is not kept either, and its request says so.
  • Fixed (Firefox): after the panel was reloaded, only the request on screen came back, and the others were lost. Firefox puts what was typed back in a reloaded page's fields, so Compose looked already in use and the kept requests were not brought back. Compose now starts empty and every kept request comes back.
  • A sixth request asks first: it names the request you looked at longest ago, and closes it only if you say so (saying when its changes would be lost).
  • Fixed: a request loaded into Compose kept the switched-off query parameters of the request shown before it.

Rule profiles that stay on (RP-1, RP-2)

  • Header and URL rules used to work only while recording. Settings → Header & URL rules → Profiles that stay on (closed until you open it) keeps named profiles: a name, the sites it covers and its rules. Switch a profile on and the browser applies its rules to those sites in every tab, with nothing recording, until you switch it off; they survive a browser restart. The rules are the ones you know: set or remove a request header, set or remove a response header, rewrite part of a URL; each can be limited to URLs containing some text. A profile with no site cannot be switched on, so a profile never applies to every site.
  • One quiet chip under the top bar names the profile that is on ("Rules on: Staging flags", or "2 rule profiles on"); its cross turns it off in one click, and the name opens the list. The chip shows only rules that really apply: a profile whose site access was taken away, or one the browser refused a rule of, is marked in the list ("Needs site access", "The browser refused a rule") and is not in the chip.
  • No new permission: the manifests already declare declarativeNetRequest and the optional host access. Switching a profile on asks the browser for just that profile's sites (or answers at once if you already allowed them at Start Recording). The privacy policy, the store text and the docs say so.
  • Import and Export share profiles as one JSON file (format in docs/RULE-PROFILES-FORMAT.md). It reads a ModHeader-style profile too. Header values that look like secrets (Authorization, Cookie, API keys, tokens) are left out of an export and come back switched off; an import never turns a profile on, and says what needs a look (no site yet, values left out, rules it could not read).
  • The recording-only rules are unchanged; a recording's own rules and a profile's rules are separate lists and never disturb each other.

Suite run options (RN-1)

  • A suite card has a quiet Run options… (closed until you open it): wait between steps (0 to 60000 ms, for an API that rate-limits), run the suite N times (1 to 100), and stop at the first failure. They are saved with the suite, shown as one line on the card while any is set, and used by Run and by Run once per row. A run that stopped at its first failure says so ("Stopped at the first failure — steps run: 2 of 3, passed: 1"), is never green, and the line is kept with the suite's last run. Stop also cuts a pause short.
  • Export as CI config writes delayMs, bail and iterations into the config (only the ones that are set), and a suite in a linked folder carries them to requestfox-ci run.
  • The CLI's assert and run take --delay-ms N, --bail and --iterations N, which override the config. --bail names how many requests were not run and lists them as skipped in a JUnit report; each repeat starts from the config's variables. A wrong value stops the run with exit code 2 before a request is sent.

The log as a table

  • A table button in the search bar shows the log as one line per call: method, path, status, time and size, plus host and flags when the panel is wider. Cards stay the default; the choice is remembered.
  • Click a heading to sort: the slowest, biggest, worst status or most flagged first, then the other way, then newest first again. The sorted heading carries aria-sort, and the line above the table says the order in words. A new call lands in its sorted place.
  • The Flags sort counts a stream's own flags (Stream error, Ended early, Paused) at their badges' weights, so a stream that errored or paused is no longer sorted as if it had no flag.
  • Drag a heading onto another to move its column there: a thin line shows where it will go, Escape cancels, and a short press still sorts. The Columns dialog lists the columns in their order with ↑ ↓ beside each (keyboard and a single click, no dragging needed), and Default order puts them back. The order is saved for the site, with the rest of its columns; taking an answer column away moves no other.
  • A row opens the call's full card under it, with every card action (Replay, Details, More…). Arrows, Home/End and Page Up/Down move between rows; Enter opens and closes; Escape closes. A jump to a call (the Timeline, a notification, a Top Issues chip) opens its row.
  • Built for long sessions: only the rows on screen are drawn, so a 5,000-call log renders and sorts within the Timeline's 300 ms budget (checked in real Chrome and Firefox by npm run test:browsers). In-flight calls and JS errors stay cards.
  • Add column above the table reads one value from each JSON answer by a path (data.items.length, $.user.id, items[*].id), offering the paths of an answer in the list as suggestions. A row with nothing there shows a quiet dash that says why. Sort by it like any column.
  • Columns (the same button) shows or hides the table's own columns (the path always shows) and takes up to four answer columns, side by side ("Add another"). The choice is saved for the site the session was recorded on; a site with none of its own starts with the answer column you chose last. A column that does not fit the panel's width waits until it is wider: your answer columns get the room before size, flags and host.
  • Group by host above the table puts a heading row over each host's calls: the host, its total, and its errors, repeats and slow calls when there are any (the tiles' own words). A click, Enter or Space on a heading folds its calls away and back. The sort still works, inside each group; the host with the newest (or slowest, or biggest…) call comes first. A jump to a call in a folded host unfolds it. Grouping is remembered; a 5,000-call log still draws only the rows on screen.

Session overview

  • A new button in the search bar opens the session's Overview: calls, errors (with the share), slow calls, repeats, what came back and the time span; the status code families; the five slowest calls; the findings by kind, in the card badges' words, each with the finding codes its calls have (RF-FAILED-5XX, RF-SLOW…; also in the Markdown); the hosts, most calls first.
  • Every line leads into the log: a slow call opens its card; a host or a finding shows only those calls (the search box's own host:, error:true, has:drift… filters).
  • Copy as Markdown puts the same in a bug report, in plain English like Copy bug report. Calls are named by host and path only: no query string (where tokens live), no headers, no bodies. It says whether the clipboard took it.
  • Calls over time: a small bar chart of how many calls started in each step of the session (a round step — 250 ms, 1 s, 10 s, 1 min… — at most 20 of them), its first and last times under it, and the same in words below ("120 calls over 240 s. Busiest: 18 in 10 s, from 12:03:10."). The words are its text alternative (the chart itself is hidden from screen readers), it has one calm colour (nothing is said by colour) and time runs left to right in every language. The Markdown names the busiest stretch.
  • A Paused finding kind: streams that stopped sending for a long time (the card's Paused badge), with their code RF-STREAM-PAUSED; a click opens the first one.
  • Fixed: what the panel says to a screen reader after you act ("Overview copied") could be replaced, before it was read, by a batch of new problems found while recording. A problems batch now waits until the panel's status line has been quiet for 5 seconds, and words still on their way never land over newer ones.

An answer's links and bytes

  • A web address in an answer's text (a card's Response, Compose's answer) is a link: a click opens it as a new GET request in Compose, in an open request of its own. On the same site, the call's headers come along (the browser's own and anything redaction hid stay out, and the status line says which to add back); to another site, none do. Ctrl/⌘- or middle-click is the browser's own.
  • In the JSON tree, a value that is an address, or a path from the site's root (/v1/items?page=2, read against the call's own address), shows a dotted line and offers Open as request first in its menu.
  • Hex (in a card beside Tree/Table, or Save for an image or protobuf kept as its bytes; in Compose beside Headers and Timing) shows any answer as bytes: an offset, sixteen bytes in hex and their ASCII per line, left to right in every language; where a line of sixteen does not fit (a 300 px panel), eight a line, so nothing scrolls sideways. A text answer is the UTF-8 of the text kept (it says so); bytes kept as base64 are shown as they are. The first 32 KB are drawn, and a longer answer says so. Copy hex copies what is drawn, Copy as base64 the whole answer. Hex is per answer, not remembered.

A list answer as a table

  • A JSON answer that is a list of objects (or holds one under a key, such as items or data.results) offers Table beside Tree, in a log card's Response and in Compose. No script: the list's place and row count, the first six columns (a nested object's keys are columns of their own), a column picker, 100 rows at a time.
  • A heading sorts (A to Z, Z to A, back to the answer's order). Copy as CSV copies every row with the columns shown, in the order shown; a text a spreadsheet would run as a formula is written as text. It says whether the clipboard took it.
  • Text, Tree or Table is one remembered choice. An answer that only looked like a list says so on the button.

Moving requests to and from other API apps

  • Compose's Import & export is two closed lists, Import and Export, each with its commonest action first (a collection, then curl; the workspace, then another app), instead of ten buttons in one row.
  • Export for another app: a collection's ··· menu, and Compose's Export list for every collection, save a file that Bruno (OpenCollection 1.0.0 YAML), Insomnia (v5 YAML) or Hoppscotch (JSON) opens. Folders, headers, off rows, query parameters, bodies, auth, collection settings and environments come along. Passwords, tokens and keys never do (there is no "export everything" here): each becomes a named variable, listed empty in the other app to fill in. The summary counts what those apps cannot hold (scripts, checks, saved responses, OAuth 1.0a / JWT / HMAC auth) and names the one next step in the other app.
  • Import reads Bruno 3+ OpenCollection files (one .yml), keeping the collection's headers, auth and variables as the collection's settings. Insomnia and Hoppscotch imports now pass a folder's or collection's headers and auth on to its requests, keep {{variables}} in query values and url-encoded bodies as written (they were percent-encoded), read Hoppscotch's url-encoded body text, and leave a {{variable}} alone when the base environment holds it empty. Bruno's older JSON export no longer doubles its query parameters.

Live streams

  • Event streams a page reads with fetch (server-sent events, NDJSON, a language model's token stream) are captured for as long as they stay open, not only their first 64 KB or 15 seconds. They are copied as the page reads them: nothing extra is read, and when the page closes a stream, the connection closes at once.
  • The newest whole events within the body limit are kept; older ones are trimmed and counted. Stop keeps the events that came so far and logs the stream straight away.
  • If the page goes away before its stream ends, the newest part seen live is kept.
  • A finished stream's card counts every event that came, says how many were trimmed (and the setting that keeps more), and why it ends there: Stop, the page closing it, a network error, or the page going away.
  • A stream's events are judged: an error event inside a 200 answer is flagged Stream error (with its message), a language-model stream that closes without its end marker is flagged Ended early, and a long pause between events is flagged Paused. A stream is Slow when its first event is late, not because it stays open. The verdict stays with the call in History, the HAR (a _stream field), the HTML report and copied text, and a HAR opened in History keeps it.
  • A language model's token stream reads as "Token stream · Events: N" with its text joined up, on its card (live and finished), in the HAR and in the copied text. This is parsing only: no model runs, and nothing is counted as tokens or cost.
  • While a stream is open, its card in the log counts the events so far, and Show events opens the newest ones as rows as they arrive, with a token stream's text joined up. The finished card replaces it when the stream ends.
  • A linked OpenAPI spec checks a stream item by item when its answer has an OpenAPI 3.2 itemSchema (server-sent events, JSON Lines / NDJSON, JSON text sequences), in the panel and in conform. An event is checked as { data, event, id, retry }, its JSON data against contentSchema, and a problem names its place in the stream (response body $[2].data). Trimmed events are listed as not checked; before, such an answer passed with nothing checked.

Cookie jar (CJ-1 to CJ-4)

  • Suites show translated errors and say why a step failed. The command-line tool refuses bad flags, answers --help and times out; rf.log() output shows under Compose.
  • Edit a saved check or header rule in place, and the comparison menu speaks words ("contains", "does not exist").
  • A suite step sends the saved request's Auth tab, as its own Send does, and a step to a host you chose Send from the extension instead for goes that way too.
  • The command-line tool says when checks are switched off or match nothing, stops before any request when a {{env:NAME}} it needs isn't set (and names it), and a diff with no baseline exits 2.
  • The security probe is called an OPTIONS check, and a clean result no longer claims CORS is fine.
  • Performance is calmer: Rate limits and Heaviest endpoints are closed rows you open when you need them, and a 300 px sidebar shows four tiles.
  • Checks and chaining read one path language: data.items[-1].id, items[*].price, filters such as items[?(@.price > 10)], .. and length(). A check on a list holds only when every item passes, and an empty list fails it.
  • The JSON Schema check understands much more of JSON Schema ($ref, allOf/anyOf/oneOf, if/then/else, formats and more) and never passes what it did not check: a keyword it does not support is listed as "not checked" and the check fails.
  • A check that cannot run marks that request's checks as failed, instead of losing the request.
  • Link an OpenAPI spec as the contract: an OpenAPI import links it, and Settings → Pass/fail checks → Contract changes it or turns it off. While a spec is linked, a call that breaks it shows SPEC MISMATCH with one line of reason, a call the spec does not have shows NOT IN SPEC, and Details lists every problem and what could not be checked. Calls to other sites (analytics, fonts) are never judged, and what RequestFox cannot check is "not checked", never a pass. With no spec linked nothing new shows.
  • Top Issues shows "Spec coverage: 34 of 52 operations seen"; a click lists the operations not called yet. The HTML report gets a Contract section, and Copy bug report a Contract line.
  • When a spec names no host and calls to a host on another site match several of its operations, one line asks "Check calls to <host> against this spec?": Check them (with Undo) or Not now, which is remembered. Settings lists the hosts added this way, each with "Stop checking".
  • A card can carry a quiet Advice badge, only for the site's own calls and local servers: a JSON or text answer sent without compression (with what gzip measured it would save, worked out in the browser), or the very same answer downloaded again with nothing a cache could use (no ETag, Last-Modified or max-age), with what a cache would have saved. Details has the fix in one line. It is advice, never an error.
  • A new check, "Same answer as last time" (Settings → Pass/fail checks, or one switch on a test suite), compares each answer with the last one for the same request. Clock times, random ids, tokens, nonces and the order of lists of records are left out on their own; you can name more paths to ignore. A changed card lists each changed value, was and now, and has "Use this answer from now on". Kept answers never hold a token, key, password, cookie or session id RequestFox recognises.
  • In the CLI the same check keeps each answer in requestfox-snapshots/ (--snapshots <dir> to choose); --update-snapshots takes the new answers, and in CI (the CI variable, or --ci) a missing saved answer fails.

Scripts

  • Pre-request and post-response scripts get rf.test("name", fn) and rf.expect(…) (Jest and Chai words), can await, and have rf.json(path), rf.getVariable, rf.crypto (SHA, HMAC, base64, UUID) and rf.sendRequest (up to 20 per run, each one logged). Their tests show on the request's card, in a suite's result and in Compose ("Script checks: 2 of 3 passed."). A script that runs too long is stopped, and the panel stays usable. Scripts run in Chrome; Firefox still refuses them, and chaining rows and checks do the same work there without code.
  • A pre-request script's changes to the request are sent; in Chrome they were lost.
  • Importing a collection with scripts warns that a script can also send requests of its own to any server. A regex longer than 200 characters is refused, with the reason.
  • The script boxes have Snippets: ready-made scripts with a comment that says why (save a token, refresh it when it runs out, check status, time and a field, sign with HMAC, add a request id and time). Typing rf. lists what scripts can use, each with a one-line note.
  • Problems show while you type, with their line and column: a text, bracket or comment never closed, a missing await, {{name}} typed inside a script, a secret typed into it, context.response in a pre-request script, and console.log. A Postman pm.* line gets its rf.* twin with Fix, or Fix all Postman lines at once.
  • A script that only saves values or checks the answer can become code-free Chaining rows and checks with Convert (with Undo); they run in Firefox too, where scripts can't. "Good habits for scripts" sums up the rest. Post-response scripts can read context.response.duration, in the panel and the CLI.

Command-line tool and CI

  • A suite's ··· menu offers Export as CI config again. Its dialog has Download the CLI: requestfox-ci.mjs, one file that ships inside the extension and runs with Node 18 or newer, with nothing to install (node requestfox-ci.mjs assert --config requestfox.config.json).
  • The CLI runs a suite the way the panel does: chaining (body, header, cookie, regex), saved auth, path variables, collection and folder settings, checks and scripts. A step whose {{token}} was never saved is not sent, and the run names the step that failed.
  • The export keeps typed-in secrets out of the file: a secret-looking value in a body, a query or a header becomes {{env:NAME}}, and the run stops before any request when that variable is not set. The dialog counts the requests, and the pass/fail checks when there are any.
  • conform --spec openapi.yaml --session session.json checks a recorded session (the extension's JSON export or a HAR file) against an OpenAPI 3 or Swagger 2 spec with the panel's own check: a line per call, the coverage and the operations not called yet; exit 1 on a mismatch. It has --reporter junit, --min-coverage and --strict, and --spec on assert and diff checks the CLI's own sends the same way.
  • "securityHeuristics": true in a CI config adds the side panel's newer security checks; off by default, so a suite that passed before still passes.
  • run <folder> runs the suites of a linked workspace folder (or a workspace export) with --suite, --env and --var; a folder with scripts needs --allow-scripts, as they are code. mock --spec api.yaml or mock --session captured.json starts a local mock server on 127.0.0.1.
  • mock --workspace <folder or file> answers each saved request's path with its first 2xx example; Prefer: example=<name>, Prefer: code=404 or Postman's x-mock-response-name / x-mock-response-code pick another. conform --spec api.yaml --workspace <folder> checks every example against the spec.
  • assert, diff, loadtest and run take --cert and --key (a client certificate), --ca (a private CA), --proxy and --insecure (staging only).
  • JUnit results carry each request's time and count errors apart from failures; a step that did not run is marked skipped.
  • requestfox-ci probe --spec api.yaml --base http://localhost:3000 makes test cases from an OpenAPI or Swagger spec and sends them: wrong types, missing required fields, values out of range or outside the enum, extra properties, malformed and oversize bodies must be refused with a 4xx (not accepted, not a 5xx), and an operation that needs sign-in must refuse a call with no or a wrong credential. Valid calls built from the examples must not fail and must match the spec. Each failure shows the request, a curl line and why, with every --header value shown as ***; --junit and --json for CI. Careful by default: this computer only unless --allow-remote, 5 requests a second, GET, HEAD and OPTIONS only unless --include-unsafe, at most 200 cases, the same cases for the same --seed, --dry-run to see them first.
  • mock --spec: Prefer: dynamic=true and the new --dynamic now make a different, schema-valid answer on each call (it used to be the same placeholder every time), and --seed repeats them. Prefer: example=name with a name the spec does not have answers a 500 that lists the names it has, as in Prism, instead of quietly sending the default.
  • YAML specs: a list item written as a flow mapping (- { name: limit, in: query }) is read as one mapping. It used to become a key named { name, so the parameters of a spec written that way were lost in the panel's import, conform, mock and probe.

Privacy

  • The page a recording starts on is redacted like every request address: a token in its query or #fragment (a magic link, a reset link, an OAuth callback) no longer reaches a report, a HAR, a bug report or an issue link.
  • Exporting settings or a workspace leaves secrets out (the token vault, client secrets, saved credentials), and importing cannot replace them.
  • Scripts run in a sandbox that can no longer navigate away.
  • One privacy policy, the same in every copy, that matches what the code does. RequestFox asks for one permission fewer (the unused activeTab).
  • The OAuth vault hint says what really happens: the passphrase is asked for again after the extension has been idle for a while.
  • Send from the extension instead goes only after your click, never with the page's cookies, and its answer is redacted like any captured body; the privacy policy says so.
  • A secret variable's value is redacted wherever it shows up in what a send captured: a URL path, any header, a body.
  • Redaction also catches S3 presigned signatures, Google API keys (key=), sig=, otp= and an OAuth code= in addresses and form bodies.
  • A field that is just a web address is no longer hidden because of its name: GitHub's "authorizations_url" or a sign-in server's "token_endpoint" show as they are. An address that carries a secret (a password, a secret-named query key, a token in its path) is still hidden.
  • Redaction also hides a PKCE code_verifier and a private_key, and no longer hides "author". The policy says a site chosen for Send from the extension stays chosen until the browser closes, and the Firefox reviewer notes explain the extension's own send.
  • Recent keeps the last 100 sends with their answers on this device, redacted, until you Clear them; a token or password typed in the Auth tab is never kept. The privacy policy, the FAQ and the Firefox reviewer notes say so.
  • Past sessions keep their full bodies and screenshots in the browser's own storage on this device; Delete and Clear old sessions remove them.
  • The CI export keeps typed-in secrets out of the file, the CLI runs scripts without your computer's environment variables, and a script's test results are stored without the values redaction hid. An export without credentials also leaves out the secrets in collection and folder settings.
  • Saved WebSocket messages stay on this device until you forget them; the privacy policy lists them.
