How to find why an API call is blocked by CORS

Record the page with RequestFox, a browser extension for Chrome and Firefox, and open the failed call: its card says CORS where the status goes, and the line under it names the rule that blocked it, such as "the response has no Access-Control-Allow-Origin header" or "the call was sent with cookies, so the server must name this page's origin, not *". Press Replay from the extension to see what the server really sent back. The fix is on the server: it must allow the page's origin.

For RequestFox 2.5.0, checked 17 November 2026.

How do I see why the browser blocked a call?

  1. Record the page

    Open the page in a tab, press Start Recording in RequestFox and do what fails, such as signing in or saving a form.

  2. Find the call marked CORS

    Press Failed above the list. A call the browser blocked for CORS shows CORS where its status would be. When the browser asked permission first, that check shows as a card of its own, marked preflight.

  3. Read the reason under it

    The line under the call names the rule that failed, for example Blocked by CORS: the response has no Access-Control-Allow-Origin header. The next section says what each one means.

  4. See what the server sent

    Press Replay from the extension on the card. RequestFox sends the call itself, where the browser's CORS rule does not apply and without the page's cookies, so you can read the status, the headers and the body the page was not allowed to see.

  5. Fix it on the server

    The server must send Access-Control-Allow-Origin with the page's origin, and for a call with cookies also Access-Control-Allow-Credentials: true. Record again: the call should pass, and leave the Failed list.

What does each CORS reason mean?

RequestFox checks in the order the browser does, from the page's origin, the call's own headers and what the server sent, and names the first rule that failed:

  • The permission check (preflight) got no response, or a status that is not 2xx. Before a call with a custom header, a JSON body or a method other than GET, HEAD or POST, the browser first sends an OPTIONS request [1]. The server must answer it with a 2xx.
  • The preflight does not allow this page's origin, the method or a header. Its Access-Control-Allow-Origin, Access-Control-Allow-Methods or Access-Control-Allow-Headers must include them. A * in Allow-Headers never covers Authorization: name it.
  • The response has no Access-Control-Allow-Origin header. The call reached the server, but the server did not say this origin may read the response.
  • The response allows another origin. The header names a different site, often the production address on a test site.
  • The call was sent with cookies, so the server must name this page's origin, not *. With credentials, the browser refuses the wildcard [1].
  • The call was sent with cookies, but the response has no Access-Control-Allow-Credentials: true.

Can I keep testing until the server is fixed?

Yes, two ways. In Compose, a request the page could not send says so, and Send from the extension instead sends it without the CORS block (and without the page's cookies). Or add a Set a response header rule under Header & URL rules that gives the page an Access-Control-Allow-Origin header while the backend's CORS isn't ready. Remove the rule when the server is fixed: it changes what the page receives, not the server.

What if the card only says "Most likely blocked by CORS"?

The browser does not tell extensions why a call failed. RequestFox marks a call to another origin that failed with the browser's generic error as most likely CORS, and names the rule only when the headers show it. If no reason shows, an ad blocker or privacy extension may have blocked the call instead: reload with your other extensions switched off. Optionally, Allow the security probe on a call (OPTIONS) in Settings → Privacy & evidence adds a Security probe (OPTIONS) item to a card's menu: after you confirm, it sends one real OPTIONS request and reads what the server says it allows. It is not a full browser preflight, so a real CORS error can still happen.
